WebP to Base64, explained

This page takes a .webp file and returns the same image as text — a data URI you can paste into HTML, CSS, JSON, or JavaScript and carry around without a file system. WebP's compression is the reason developers reach for it over PNG for photographs and over GIF for animation: smaller source bytes mean a shorter Base64 string riding along inside whatever document you paste it into.

How to use it

<img src="data:image/webp;base64,UklGRni..." alt="image" />

.hero { background-image: url(data:image/webp;base64,UklGRni...); }

What the encoder does to your file

Mechanically, nothing touches the pixels. The browser reads the file as raw bytes, and Base64 maps every three bytes onto four characters drawn from a fixed 64-symbol alphabet. The result is a longer string that unpacks to exactly the bytes you dropped in. That is why alpha, animation, and metadata all survive: the encoding step has no opinions about image content, only about bytes.

Browser support

Every current major browser decodes WebP, and a data URI does not change that: support is a property of the format, not of the delivery method. The compatibility question only reappears on machines old enough to predate WebP entirely — the same machines that would also fail on a hosted .webp file. If one of those is genuinely in your audience, the fix is a fallback asset, not a different encoder.

Sizing before you paste

The string is always longer than the file — about a third longer once the Base64 overhead lands, before any transport compression gets involved. When a budget matters, run the file through the Base64 image size calculator first. Remember too that an inlined image gives up its own cache entry: it downloads again with every document that contains it, instead of being reused across pages the way a separate file is.

Lossless format versus lossless bytes

Two meanings of "lossless" get conflated around WebP and Base64, and separating them prevents most of the confusion. WebP the codec has a lossless mode (VP8L) and a lossy mode (VP8), decided when the file was created — that property is baked into the bytes. Base64 encoding is lossless at the byte level no matter which mode the file uses: it maps bytes to text and back without judging their content, so it never re-compresses anything. Encode a lossy WebP here and the data URI unpacks to that same lossy WebP, artifacts included; encode an animated or alpha-bearing file and every frame and channel comes through, because those are bytes too.

The data URI always carries the image/webp MIME label, and the encoded body starts with UklGR — the Base64 spelling of the RIFF container header that opens every WebP file.

Choosing where the data URI goes

  • An <img> src. The simplest placement, and the only one that carries alt text with it. Use it for content images small enough that a request would cost more than the bytes do.
  • A CSS background-image. The natural home for decorative art — textures, badges, watermark-style flourishes. No alt text involved, and the string lives with the stylesheet instead of the markup.
  • A <picture> element. Handle with care: the fallback chain needs a separate URL for each candidate, and a data URI gives you exactly one asset already fixed to its format. When a page truly needs WebP-with-PNG-fallback behavior, serve real files through <picture> and reserve data URIs for cases where a single format is enough.

The through-line across all three placements: inline when the asset is small and the alternative is an extra request; keep a real cached file when the asset is large or shared across many pages.

Nothing leaves the browser

The file you drop in is read with FileReader and encoded in memory. There is no network step anywhere in the flow, so unreleased product art, confidential screenshots, and client deliverables stay on the machine they started on.

When inlining a WebP is the right call

A data URI is a trade: you spend document size to avoid a network request. The trade clearly favors inlining in a few situations and argues against it nearly everywhere else:

  • Inline small UI assets that ship on nearly every page load — icons, logos, control glyphs. One fewer request, and no moment where the layout waits on an image that has not arrived yet.
  • Inline when the deliverable is one file. A spec emailed as a single HTML document, a demo attached to a ticket, an offline copy of a page — none of those can reliably reference sibling image files.
  • Keep a real file for anything large. A hero image inlined into markup has to arrive before the page can settle, while a separate file streams in parallel and caches on its own terms.
  • Keep a real file for assets reused across pages. An inlined copy travels with every page that contains it; a shared file downloads once per visitor and is reused after that.

WebP shifts these thresholds in the encoder's favor compared with PNG — the same visual quality costs fewer source bytes, so more assets fall inside the "small enough to inline" range — but it does not change the shape of the trade. Measure the string, compare it against what the document already weighs, and let the numbers make the call.

Frequently asked questions

What does a WebP Base64 string start with?

A WebP data URI starts with data:image/webp;base64, and the body begins with UklGR — the Base64 signature of the WebP (RIFF) header.

Will a Base64 WebP work in every browser?

It displays in any browser that supports WebP — all modern browsers (Chrome, Firefox, Safari, Edge). Base64 doesn't change format support, only how the bytes are delivered. Keep a PNG/JPG fallback only for very old browsers.

Is the conversion private?

Yes. Everything runs in your browser with the FileReader API. The WebP is never uploaded to any server.

Is Base64 encoding lossless for a lossy WebP?

Yes — the two senses of "lossless" are separate. Base64 is lossless at the byte level for any file, so a lossy WebP comes back as the identical lossy WebP. The codec's lossiness happened when the file was created, not during encoding.

Does encoding preserve animation and transparency?

Yes. The encoder reads raw bytes and maps them to text without touching image content, so animated frames, the alpha channel, and metadata all arrive inside the data URI intact.
