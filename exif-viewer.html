What EXIF actually is

EXIF is a small binary block that a camera writes next to the pixels. In a JPEG it sits in an APP1 segment immediately after the start-of-image marker; in a PNG it lives in an eXIf chunk; in a WebP it is an EXIF chunk inside the RIFF container. Within the block are directories — IFD0 for device basics, a sub-directory for shooting settings, a separate one for GPS — and each directory holds tags made of an ID, a type, a count, and either an inline value or an offset pointing at one. None of it is compressed with the picture, so a parser can read the entire thing in microseconds without decoding a single pixel. That is why the field list can appear here before the thumbnail has finished painting.

The block is stamped at capture, then rewritten by every tool that touches the file afterwards. Some editors append their own tags, some rebuild the block from scratch, some discard it. Two exports of the same shot can therefore disagree about the camera while the pixels stay identical.

The fields worth reading

  • Make, Model, LensModel. What produced the file. Enough to separate a phone from a camera body with a lens attached, or to check which lens you had mounted at 35 mm.
  • ExposureTime, FNumber, ISO, ExposureBias, FocalLength. The settings behind the frame — the practical way to reverse-engineer a look you like, or to sanity-check a claim about available light.
  • DateTimeOriginal against DateTime. The first is stamped when the shutter fired; the second is rewritten on save. A wide gap between the two says the file was re-saved long after the shoot.
  • GPS latitude and longitude. Three rationals per axis plus a hemisphere reference, with altitude, a UTC timestamp and a heading in the same group. The viewer turns them into decimal degrees and hands you a map link.
  • Orientation. A value from 1 to 8 telling a renderer how to rotate or mirror the stored pixels for display.
  • Software, Artist, Copyright. Which editor saved last, and what rights string the author attached to the file.
  • MakerNote. An opaque vendor block. It can carry serial numbers, lens IDs, focus distance and scene flags, and no public standard describes all of it.

Why the inspection has to stay local

Coordinates are the one field that says where you physically stood, which makes "just upload it to a free online viewer" a strange trade. By the time a stranger's server finishes parsing the file, it already knows your address; the decision you came to make has been made for you. The same logic applies to the copy sitting in their logs, their CDN cache and their analytics pipeline.

This page never forms that request. The drop handler reads the bytes the browser already holds, hands them to the parser, and renders the result — no multipart form, no base64 body, no worker shipping the file somewhere else. You can audit it in the Network panel: look for any request that carries the image, and there is none. Stronger test: disconnect the network and inspect a file anyway. A tool that needs a server cannot parse offline, and this one does. If the tab dies on a very large image, that is the browser's memory ceiling, not a transfer.

What a viewer cannot tell you

  • Who took the photo. Make and Model describe a product line sold in large numbers. A serial number buried in the MakerNote narrows it to one body, which is still not a person, and is still editable.
  • Whether the file is untouched. Every one of these fields is bytes. A script can set the capture date to anything, and removing metadata is a single function call in most libraries.
  • That a clean file was scrubbed. Screenshots, forwards through chat apps, CDN re-encodes and canvas exports all produce files with no EXIF. Absence describes the pipeline, not the intent.
  • What used to be there. Once a platform or a strip tool dropped the block, those values are gone. There is no undo stored inside the image.

Why a photo displays sideways

Camera sensors are mounted at an angle to the body, so the raw pixel grid is often landscape even when you held the phone upright. The firmware writes the pixels as captured and records the correction in the Orientation tag; renderers that honor the tag rotate on display, renderers that ignore it show the frame on its side. This is also why metadata removal needs care: the full strip on the metadata remover keeps that single tag on purpose, so a cleaned file still opens the right way up. What stripping cannot fix is a file whose pixels were physically rotated and then mislabeled — there you need to rotate and re-save, which does touch the image data.

Check before you upload

A quick triage, in the order most people hit it. Marketplace and classifieds listings: assume the full-size original is downloadable, so look at the GPS group before you post. Bug reports and support threads: screenshots are usually clean, camera photos are not. Client mock-ups and portfolio pieces: the device string and capture date can identify the studio or the date of the shoot. Publishing through a CMS that keeps originals: clean the file itself, because the copy on the CDN inherits whatever you uploaded. Sorting your own archive: leave the metadata alone, it is how you search by gear and place.

When something needs to go, strip everything with the metadata remover, take only the coordinates out with the GPS tool, or follow the iOS-specific notes on the iPhone page. What these pages do with your file is described on the privacy page.

Formats this viewer reads

JPEG, PNG and WebP are parsed field by field. HEIC is the exception worth knowing about: Safari can decode an iPhone HEIC, but the code path for it re-encodes the image, so you get a summary of what was found instead of a tag-by-tag list. Export a JPEG from Photos when you need to read the entries individually. Anything else is reported as unsupported rather than guessed at — TIFF carries EXIF as well, but it sits outside this tool's scope. One more quirk: some cameras append a multi-picture block holding an extra embedded frame, and the viewer lists the main image's tags without showing that preview as a separate photo. For the format-by-format mechanics, see the removal guide.

Frequently asked questions

Does the EXIF viewer upload my photo?

No — parsing happens in your browser's memory and results render on the page. The Network tab stays empty.

How do I check where a photo was taken?

Drop the file in; if a GPS group exists you'll see coordinates and an "open in Google Maps" link. No GPS group means no location data.

What's the difference between EXIF and metadata?

EXIF is the camera-written metadata standard (settings, timestamps, GPS). Files may also carry XMP and IPTC blocks — the viewer shows whatever the file actually contains.

Why does my screenshot have no EXIF?

Screenshots and re-saved downloads typically never had the original block, or lost it in transit. "No metadata found" is normal for them.

Can I export what the viewer finds?

Yes — "Copy as JSON" puts every discovered field on your clipboard.

Can the metadata be faked?

Easily. Every field is plain bytes, so any library or script can rewrite the capture date, the camera model or the coordinates. Read the values as context about the file, not as proof of anything.

Does inspecting a photo modify it?

No. The viewer opens a read-only copy of the bytes and writes nothing back. Your file on disk keeps its name, its size and its metadata; use the metadata remover if you actually want a cleaned copy.
