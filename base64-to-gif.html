Base64 to GIF, explained

Paste a Base64 string or a data URI, preview the picture, and save a .gif file. What sets the GIF page apart from the other decode pages on this site is that nothing here re-encodes your image: the bytes you download are the bytes the string was encoding, verified against the GIF file signature before a download link is created.

Byte passthrough, and why it has to work that way

Browsers decode GIF natively — that is why the preview animates. What browsers cannot do is write GIF: there is no GIF encoder behind the canvas API, so no browser-side tool can redraw an image and save it as an animated GIF. A page that outputs GIF honestly has exactly one option, which is to hand back the original bytes unchanged. That constraint is why the file you download here always matches its source — same frames, same palette, same loop behavior, byte for byte.

The practical payoff shows up in round trips. If the string came from GIF to Base64, decoding it here returns the exact file you started with. Nothing between the two steps ever touched the image data, so there is nothing to degrade.

The 256-color ceiling belongs to the format

GIF stores at most 256 colors per frame in its palette. The limit is part of the format definition, so it appears in every GIF ever made — this tool neither adds it nor removes it. A source GIF with a well-built palette (icons, logos, simple UI captures) decodes looking precisely as it always did. A source GIF that was converted from a photograph already went through palette reduction and dithering somewhere upstream, and that posterized look comes back in the download too, because passthrough preserves it. When the image is photographic, GIF was the wrong container before it was ever Base64 — decode through Base64 to image to recover the original format instead.

When GIF is the right target, and when it is not

  • Right target: you have GIF bytes and want the GIF file back, animation included. Passthrough makes this the safest place to do it.
  • Right target: flat artwork or a short loop, where the palette limit and the format's universal support matter more than its size inefficiency.
  • Wrong target: photographs. JPEG or WebP represents them better at smaller sizes, and no amount of decoding changes what the palette already threw away.
  • Wrong target: hoping for compression wins. GIF's compression predates modern codecs; for still images, PNG or WebP files come out smaller at equal or better quality. For animation, animated WebP is the modern alternative, and Base64 to WebP covers the decode in that direction.

What counts as valid input

  • Full data URI. data:image/gif;base64,R0lGOD... — the MIME label names the format, and the signature check still verifies the bytes underneath it.
  • Bare Base64 body. The long string by itself, with no data: prefix. The GIF header check is what decides whether it becomes a downloadable file.

Animated GIFs living inside a data URI

The same passthrough property applies while the GIF is still a string. A data URI built from an animated GIF contains every frame, because Base64 encodes bytes rather than pixels. Drop that URI into an <img> tag or a CSS background-image on a web page and the animation plays exactly as the file would. The picture changes outside the browser: plenty of email clients strip data URIs outright, animated or not, which makes inlined GIFs a web technique rather than a mailing one.

Reading the two GIF headers

Before offering the download, the decoder checks the head of the decoded data for GIF87a or GIF89a. The two names are revisions of the same spec: 87a is the original 1987 definition and predates animation, while 89a introduced the extensions that carry frame timing, transparency flags, and loop counts. Nearly every GIF you encounter today, still or animated, is 89a. If the check fails, the string was never a GIF to begin with, and the tool stops rather than labeling a broken file .gif.

Everything happens locally

Decoding and the signature check both run in the page; no request leaves the browser carrying your data. Paste strings from private repositories, internal tools, or client projects freely.

Checking the file you got back

Passthrough decoding makes verification straightforward, because there is no re-encode to second-guess. Three checks cover most of what can go wrong, and all three point at the string rather than the decoder:

  • File size. The .gif on disk should weigh exactly what the source GIF weighed. A mismatch means the string was truncated, padded, or built from a different version of the file — not that this page altered anything.
  • Animation. Open the download in a browser tab instead of a static image viewer, and confirm the loop count and per-frame delays match what you expected.
  • Palette edges. If the source GIF came out of a photo conversion, inspect gradients and small text in the first frame. Palette artifacts were already inside the bytes; they will not appear or disappear here.

Frequently asked questions

How do I convert a Base64 string to a GIF?

Paste the Base64 string or full data URI into the box and click Decode to GIF. The tool verifies the GIF signature, previews it, and downloads the original .gif bytes.

Can this decoder handle animated GIFs?

Yes. The downloaded file uses the original GIF bytes, so every animation frame, delay, and loop setting is preserved.

Is the decoder private?

Yes. Decoding happens entirely in your browser. Nothing is uploaded, so your data stays on your device.

Is the downloaded GIF identical to the original file?

Yes. The decoder verifies the GIF87a/GIF89a header and then passes the original bytes through, so frames, palette, timing, and loop count come back exactly as the string encoded them. Nothing is re-encoded.

Can I turn a PNG or JPEG string into a GIF here?

No. The page accepts GIF data only, and the signature check rejects anything else before a download is offered. Format conversion would require re-encoding, which browsers cannot do for GIF.
