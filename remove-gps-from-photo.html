What a GPS tag physically holds

Coordinates are not stored as the decimal pair you see in a map URL. Latitude and longitude each arrive as three rational numbers — degrees, minutes, seconds — with two separate ASCII tags carrying the hemisphere (N or S, E or W). Altitude is another rational, paired with a reference byte that says whether it is above or below sea level. The same directory can hold a UTC date stamp and a time-of-day split into three rationals, an image direction in degrees from true north, and the map datum, which in practice is almost always WGS-84. Because the numbers are rationals, an untouched dump reads like 44/1, 26/1, 3344/100 — a form that means nothing until something divides it out. The viewer on this site does that division and shows both notation styles.

A file either has that directory or it does not. There is no partial location, no fuzzy city-level guess stored alongside: if the GPS group is absent, the file carries no coordinates at all. This is why the check is binary and takes one second, and why "it's probably fine" is a bad default.

Where geotagged files actually escape

The obvious channels are the ones people already distrust. The ones that cause trouble are the ordinary, workaday paths where nobody thinks about bytes:

  • Marketplace and classifieds listings. A "view full size" link usually serves the file you attached, byte for byte. Three listings shot from the same balcony describe one address.
  • Hobby forums and imageboards. Attachments are commonly stored and served unmodified, and they stay indexed long after the thread dies.
  • Email attachments. The ordinary SMTP path does not rewrite image metadata, so the recipient gets what you sent, coordinates included. Gateway software at either end may behave differently, which is another reason not to count on it.
  • Chat apps sending "as file" or "as document". The compressed-photo path usually re-encodes and drops the block; the document path is designed to preserve the original. Same app, different result.
  • Cloud drive share links. The shared object is the uploaded object. Anyone with the link can download it and read the EXIF.
  • Dating and social apps. Behavior varies by product and changes without notice. Some re-encode on upload, some keep the original behind the download link, and you cannot tell which from the outside.
  • Your own CMS. If uploads are stored as received and served from the same object, cleaning the local file before upload is the only step that helps.

Two honest ways to remove it

The first family rewrites the container. On a JPEG this page walks the marker segments, finds the EXIF APP1 block, rebuilds it without the GPS directory, and copies the compressed scan data across untouched; on a PNG it rebuilds the eXIf chunk the same way, and on WebP it rewrites the EXIF chunk. The pixels are never decoded, so nothing is re-quantized and the output opens at exactly the same quality. Two other segments are dropped at the same time on purpose: XMP can repeat the coordinates in XML, and the multi-picture block can hold a second, smaller frame. Leaving either in place would defeat the point of a location strip.

The second family decodes the image and writes a new file. Draw the photo into a canvas, export it, and the metadata cannot survive — the canvas holds pixels and nothing else. That approach is thorough, and it costs you a JPEG generation: the output is re-compressed, the file size changes, and any color profile the original carried may be lost. For a portfolio image or a print, that matters. For a quick forum post, it usually does not.

A third option exists for batches on a desktop: a command-line tag editor can clear the location group in place across a folder. If you already have that tool installed, it is the fastest route for hundreds of files. For one photo on a machine you do not want to configure, this page is quicker.

Approaches that look like they work

A few popular habits remove less than people assume. An in-app "hide location" switch in a social product usually governs that product's own upload pipeline; export the same file to a drive and the tag is still there. Renaming the file, changing its extension or putting it in a ZIP changes nothing about the bytes inside. Many photo editors copy the source EXIF onto their output as a feature, so cropping or color-grading a geotagged photo can produce a new file that still carries the old coordinates. And a screenshot is genuinely clean — capturing the frame drops the original block entirely — but you lose resolution, you may capture interface chrome around the picture, and you end up with a PNG that is often larger than the JPEG you started with. It is a real fix with a real cost, not a free one.

Confirm the strip in about ten seconds

Do not trust the file name. A copy saved as photo_no-gps.jpg is only a naming convention; nothing enforces it. Reopen the downloaded copy in the EXIF viewer and read the summary line: it should report fewer entries and state plainly that no GPS location is embedded, while camera and date rows remain. The entry count should drop by a handful, not to zero — a full wipe means you used the wrong mode or the wrong tool. Comparing file sizes gives a second signal: removing one directory typically takes a few hundred bytes, whereas a drop of tens of kilobytes suggests the image was re-encoded.

Stop the tag at the source

Cleaning old files fixes the past; a camera setting fixes the future. On an iPhone, open Settings → Privacy & Security → Location Services → Camera and set it to Never. On Android, open the Camera app's settings and switch off the location-tag option, whose label differs by manufacturer. Then take one test shot and drop it into the viewer: no GPS group means the change took effect. The trade-off is real — your library can no longer group photos by place, and a few third-party camera apps lose features that depend on location. Plenty of people keep tagging on and clean files at publish time instead, which is why this page exists.

When location is not the only thing you want gone

Keeping the camera and date is often deliberate: a photojournalist can show when a frame was shot and with what, without disclosing where. If that is not your situation — a client deliverable, a public profile picture, a photo of your own front door — the wider strip on the metadata remover clears the device strings as well, and the iPhone page covers the share-sheet shortcuts that already handle location on iOS. Either way, the image itself is unchanged: removing metadata never crops, never resizes, and never alters what a viewer sees.

Frequently asked questions

Does removing GPS change the other metadata?

No — the EXIF block is rebuilt without the location entries and every other field survives unchanged. Pixels are copied byte-for-byte.

Is the photo uploaded anywhere?

No. The stripping happens in your tab; the Network tab will show no image transfer.

How accurate is photo GPS?

Roughly 5–20 meters outdoors — house-level precision, which is why it's worth removing before public sharing.

How do I stop my phone adding GPS?

iPhone: Location Services → Camera → Never. Android: Camera settings → disable location tags. New photos will carry no coordinates.

Do social platforms strip it anyway?

Some re-encode and drop EXIF, but email, document-style messaging, cloud drives and many forums preserve the original file. Cleaning first means you never have to guess.

Does the cleaned file keep the same checksum?

No. Dropping the location directory changes the bytes, so any SHA or MD5 you recorded for the original no longer matches. That is expected: the pixels are identical, the container is not.

Can the coordinates be recovered from the cleaned copy?

Not from that file. The directory is gone, and nothing else in a JPEG, PNG or WebP duplicates it once XMP and the multi-picture block are dropped too. Any earlier copy you still have, or an upload made before cleaning, is a separate question.
