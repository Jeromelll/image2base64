Where inline images hide — and how to get them back out

Encoding images as Base64 is half of the story. Build tools inline every asset into one CSS bundle, single-file HTML exports carry their images inside the markup, email templates embed logos as data URIs to survive image blocking, and APIs hand images back as Base64 strings inside JSON. The moment you want the actual file back — to edit it, re-compress it, or drop it into a design tool — you are stuck eyeballing a ten-thousand-character string.

This page is the reverse direction of the Base64 encoder, built for bulk: paste the whole stylesheet, page source, or JSON dump, and it pulls out every data:image/…;base64 payload at once.

Where data URIs actually sit in a stylesheet

background-image is the obvious slot, but the same syntax appears in the background shorthand, mask-image and -webkit-mask-image, border-image-source, list-style-image, cursor, and inside @font-face blocks where src carries a font. Media queries do not change the grammar: a retina override that swaps in a 2x asset still writes url(data:image/png;base64,…) inside @media (min-resolution: 2dppx). In HTML the string shows up in src, srcset, poster and inline style attributes. CSS-in-JS libraries — styled-components, Emotion, an arbitrary-value class in Tailwind — emit ordinary <style> elements, so the payload can be present in the rendered page while the source files you have contain no trace of it.

How to use it

  1. Paste the source text. CSS, HTML, inline JS, raw email source, JSON — anything containing data URIs.
  2. Press Extract. Each found image appears as a card with a preview, its detected format, decoded size and pixel dimensions.
  3. Download what you need. Every card has a download button that saves the file with the correct extension — a PNG payload downloads as .png, a JPEG as .jpg, and so on.

Pulling one out by hand

Worth knowing even if you use the tool, because the manual path is what you fall back on when the payload sits somewhere a scanner cannot reach — inside a string built at runtime, for example.

  1. Search for the scheme, not the word. Look for data:image/. In a minified bundle the whole file is one line, so a line-based search returns a single hit thousands of characters wide; search for the literal prefix instead.
  2. Copy the entire token. Include data: through the closing delimiter. If the payload has no obvious end, take everything up to the next ", ', ) or ;.
  3. Strip the wrapper. Keep the characters after the first comma. The MIME type before it — image/png, image/jpeg, image/svg+xml — tells you which extension the bytes belong in.
  4. Decode. printf '%s' "$b64" | base64 -d > out.png from a shell, or atob() into a Uint8Array in the browser. JavaScript's atob() rejects whitespace, so unwrap the string first.
  5. Open the result. A viewer that renders it means the extraction worked. A viewer that refuses means the payload was truncated or mislabeled.

How the extraction works

Base64 has a strict alphabet — A-Z a-z 0-9 + / = — so the scanner walks the text for data: MIME declarations followed by a valid Base64 run and stops exactly where the payload ends, even inside quotes or url() wrappers. Identical payloads are reported once (duplicates are marked), so a stylesheet that reuses the same sprite four times gives you one download, not four. Decoding is lossless: the downloaded bytes are a byte-for-byte copy of the original image, transparency and metadata included.

Quoting, and why url() is pickier than it looks

url() takes three forms: bare, single-quoted, double-quoted. The bare form ends at the first ) and disallows whitespace, quotes and parentheses, so a Base64 payload — + and / are fine, ) never appears — survives it, while a percent-encoded SVG full of parentheses does not. Quoted forms accept almost anything except their own delimiter, which is why a payload containing an apostrophe breaks a single-quoted URL; SVG path data and font-family names produce those apostrophes often enough to matter. Copy the surrounding quotes along with the token. If you drop them, you either cut the tail at the first quote character inside the string or drag the next declaration into your selection.

Base64 is not the only kind of data URI

An SVG can be inlined two ways: data:image/svg+xml;base64,PHN2Zy…, and the percent-encoded form data:image/svg+xml,%3Csvg%20…. Only the first is Base64. The second is UTF-8 markup with reserved characters escaped, and it decodes with decodeURIComponent(), not atob(). A scanner looking for Base64 will skip it, and a Base64 decoder run over it produces garbage rather than an error. The trade-offs between the two forms, including which one compresses better inside a stylesheet, are laid out in SVG: data URI vs inline SVG. If you need to go the other direction and produce a URI rather than consume one, the data URI generator takes a file and returns the full string.

Three failures that look like corrupt files

  • Double encoding. Some pipelines Base64 the whole data URI instead of the bytes, so one decode hands you text starting with data:image/png;base64,. That is a signal to decode again, not a broken image.
  • Percent-encoding stacked on Base64. A token containing %2F or ending in %3D%3D was URL-escaped after encoding. Unescape first, then decode — the reverse order fails every time.
  • Chunks joined at runtime. Bundlers sometimes emit "data:image/png;base64,"+"iVBORw0…", or split a long literal across a line continuation. A scanner that stops at the first quote returns only the prefix, and the payload waits in the next literal.

Checking that the bytes are a real image

Decoded data either parses or it does not, and the first bytes say which format you actually received: 89 50 4E 47 for PNG, FF D8 FF for JPEG, 47 49 46 38 for GIF, 52 49 46 46 ("RIFF") for WebP, and an opening <svg or <?xml for SVG. When a card previews blank but its size looks plausible, compare those bytes against the declared MIME type. A mismatch means the string was mislabeled upstream, and the extension should follow the bytes rather than the label. For a single payload you can also paste it into the Base64 to image decoder, which reports a decode error instead of showing an empty frame.

Typical situations

  • Recovering assets from a built site. The original PNGs are gone, but the bundle has them inline — extract and save them back.
  • Inspecting what a page actually ships. A "tiny" stylesheet hiding 400 KB of inlined hero images is easy to spot once every payload's decoded size is listed.
  • Pulling images out of API or database dumps. JSON records that store avatars as Base64 text become real files again.
  • Email forensics. Raw MIME source with tracking pixels embedded as data URIs, made visible.

What it does not do

Percent-encoded SVGs (data:image/svg+xml,%3Csvg…) are not Base64 and are skipped — those decode with plain URL unescaping instead. And an image whose payload was truncated in a copy will fail to preview; the tool tells you which cards are broken rather than silently downloading corrupt files. Extraction is also often the first step of an audit: if the inline assets you just pulled out are the ones a policy should be restricting, data URIs and CSP explains what an img-src or default-src directive does to them.

Frequently asked questions

How do I extract an image from a CSS file?

Paste the CSS and press Extract. The tool scans for every data:image/...;base64 URI, previews each one and provides a download with the correct extension — all locally in your browser.

Can it extract images from HTML and JSON too?

Yes. Base64 uses the same alphabet everywhere, so the surrounding format — CSS, HTML, JS, email MIME, JSON — does not matter. If the text contains data URIs, they get found.

What about URL-encoded SVG data URIs?

Percent-encoded SVGs (data:image/svg+xml,%3Csvg…) are not Base64 and are skipped. Re-encode the SVG with the SVG to Base64 converter if you need it in this form.

Does the extracted image keep its original quality?

Yes — Base64 is lossless, so the downloaded file is byte-for-byte identical to the original image, transparency and metadata included.

Why can't I preview one of the extracted images?

Almost always a truncated payload from a partial copy. The card is marked so you know the download would be corrupt, and the payload is still there for debugging.

Is my CSS or HTML uploaded anywhere?

No. Extraction, preview and download all run in your browser with a local scan. Nothing is sent to any server.

Why does the extracted file not open?

Two usual causes. Either the payload was cut short while copying — the decoded byte count will not match the character count you would expect from the Base64 length — or the URI was percent-encoded as well as Base64, so it needs unescaping before decoding.

Can I extract images from a minified CSS bundle?

Yes, with one caveat. The scan is text-based, so length is irrelevant, but a bundle that splits a payload across concatenated string literals hides the tail from any scanner. In that case grab the pieces from the source map or from the rendered page.
